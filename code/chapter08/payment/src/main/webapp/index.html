Payment Service

MicroProfile Config & Fault Tolerance Demo

About this Service

The Payment Service demonstrates MicroProfile Config integration with custom ConfigSource implementation and comprehensive Fault Tolerance patterns.

It provides endpoints for managing payment configuration and processing payments with retry policies, circuit breakers, and fallback mechanisms.

Key Features:

  • Custom MicroProfile ConfigSource with ordinal 600 (highest priority)
  • Dynamic configuration updates via REST API
  • Payment gateway endpoint configuration
  • Real-time configuration access for payment processing
  • MicroProfile Fault Tolerance with Retry Policies
  • Circuit Breaker protection for external services
  • Timeout protection and Fallback mechanisms
  • Bulkhead pattern for concurrency control

API Endpoints

  • GET /api/payment-config - Get current payment configuration
  • POST /api/payment-config - Update payment configuration property
  • POST /api/authorize?amount={amount} - Authorize a payment (with @Retry, @Timeout, @Fallback)
  • GET /api/health/gateway - Check gateway health (with @CircuitBreaker, @Timeout)
  • POST /api/notify/{paymentId}?recipient={email} - Send payment notification (with @Asynchronous, @Bulkhead, @Timeout, @Fallback)

Fault Tolerance Features

The Payment Service implements comprehensive fault tolerance patterns across three service methods:

🔄 Retry Policy

Applied to: authorizePayment()

  • Max Retries: 3
  • Delay: 2000ms between retries
  • Jitter: 500ms randomization
  • Retry on: PaymentProcessingException
  • Abort on: CriticalPaymentException

⚡ Circuit Breaker

Applied to: checkGatewayHealth()

  • Failure Ratio: 50%
  • Request Threshold: 4 requests
  • Recovery Delay: 5000ms
  • Success Threshold: 2 consecutive successes

⏱️ Timeout Protection

  • Authorization: 3000ms per attempt
  • Gateway Health Check: 2000ms
  • Payment Notification: 5000ms

🛟 Fallback Mechanisms

  • Authorization: Returns status "pending" — payment queued for processing
  • Notification: Queued for retry via fallbackSendNotification()

🧱 Bulkhead Pattern

Applied to: sendPaymentNotification() (@Asynchronous)

  • Concurrent Requests: 10 maximum
  • Waiting Task Queue: 20 requests
  • Excess Requests: Rejected immediately
  • Recovery: Automatic when load decreases

Configuration Management

This service implements a custom MicroProfile ConfigSource that allows dynamic configuration updates:

  • Configuration Priority: Custom ConfigSource (600) > System Properties (400) > Environment Variables (300) > microprofile-config.properties (100)
  • Payment Properties: payment.gateway.endpoint, payment.retry.maxRetries, payment.retry.delay, payment.circuitbreaker.failureRatio, payment.circuitbreaker.requestVolumeThreshold, payment.timeout.duration
  • Update Method: POST to /api/payment-config with {"key": "payment.property.name", "value": "new-value"}

Testing Fault Tolerance

Test the fault tolerance features with these examples:

  • Trigger Retries: POST /api/authorize?amount=100 — authorizePayment() has a 60% simulated failure rate, so retries fire on most requests
  • Circuit Breaker: Repeated calls to the internal checkGatewayHealth() method (40% simulated failure rate) will open the circuit after 2 failures in 4 requests
  • Timeouts: Each authorizePayment() attempt simulates 1500ms latency against a 3000ms timeout; health checks simulate 500ms against a 2000ms timeout
  • Fallbacks: After all retries are exhausted, authorizePayment() returns a pending-status fallback response instead of an error
  • Bulkhead: Generate >10 concurrent requests to sendPaymentNotification() to see requests rejected when the queue of 20 fills up
